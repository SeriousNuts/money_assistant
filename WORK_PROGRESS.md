Дата фиксации: 26 октября 2026 года. Этот файл — рабочая заметка для следующего сеанса, **не описание готовых функций**.

## Запрос владельца

1. Контакты должны загружаться в приложение: поиск и выбор нескольких человек одним действием должны работать на его устройстве. Владелец сообщает, что в установленной у него версии по-прежнему нельзя выбрать несколько контактов.
2. После создания счёта можно добавлять участников. При добавлении каждого нужно спросить сумму долга или предложить «Добавить сейчас, указать позже» (тогда долг — 0 ₽).
3. Существующие счета можно редактировать без потери оплат.
4. К одному счёту можно прикрепить несколько чеков. Нужен простой интерфейс при большом числе чеков и позиций.
5. Нумерация версий: следующий выпуск — `1.4.2`, затем `1.4.3` и далее; **не переходить на 1.5 без прямой просьбы**. Периодически коммитить и отправлять изменения в GitHub от `SeriousNuts`.

## Устройство существующего кода и риски

- `app/src/modern/java/com/example/myapplication/ContactSelectionActivity.java` читает `ContactsContract.CommonDataKinds.Phone.CONTENT_URI` после READ_CONTACTS, показывает список с поиском и чекбоксами. Только контакты с номером попадают в список; стоит учитывать контакты без номера, синхронизацию, загрузку/ошибки и явную обратную связь о числе выбранных. `AfterContact` получает имена и телефоны через результат Activity.
- `AfterContact.java` — редактор только **нового** счёта; удаление/добавление человека или изменение доли очищает `bill.lines`, а добавление контактов при заданной общей сумме перераспределяет **все** доли поровну. Это недопустимо для уже оплаченного счёта. Нужны отдельные безопасные сценарии для существующего счёта с явным вводом долга и сохранением чужих долей и оплат.
- `MainWindow.java` — детали и отметка оплаты; сейчас нет действий «Редактировать»/«Добавить участника»/«Чеки».
- `BillDocument.java`: `people` и единый список `lines`; `ReceiptLine.java` содержит позицию, сумму, прямоугольник разметки и индексы назначенных участников. Для многих чеков нужна модель списка чеков с отдельным id, названием, фото и позициями, а также чтение старого поля `lines` **без потери данных**. При удалении/перестановке участников индексы в позициях необходимо корректно обновлять или запретить опасную операцию с объяснением.
- `ReceiptActivity.java` сейчас хранит ровно одно фото `files/receipts/<bill-id>.jpg`. Замена фото очищает разметку; интерфейс отображает все позиции карточками в ScrollView, что неудобно при большом количестве. Нужен обзор чеков (краткая карточка/сумма/количество позиций), отдельный экран одного чека с поиском по позициям/компактным списком, добавление/редактирование/удаление чека с подтверждением; фото каждого чека в отдельном файле. Не удалять фото и записи при ошибке/отмене до успешного сохранения.
- `ReceiptCalculator.java` распределяет позиции по участникам; сумма чеков и вручную введённые долги требуют чёткого правила, чтобы не перезаписывать оплаты и ручные доли. Возможный принцип: новые чековые позиции добавляют рассчитанные доли к существующим вручную введённым; отдельно показать итог и исходные суммы. Зафиксировать правило тестами до изменения данных.
- `BillRepository.java`: `save` в деморежиме заменяет счёт, **копируя paid по индексу**, а в облаке транзакция создаёт счёт **только если его ещё нет**. Для правки существующих счетов нужна корректная атомарная операция обновления обоих видов хранилища с проверкой одновременных изменений, согласованными документами участников и без потери `paid`/`ledgerJson`. `addBill` при загрузке из облака заменяет участников из `ledgerJson` данными дочерних документов. Обычного вызова `save` для редактирования недостаточно.

## OCR и черновики: 28 октября 2026 года

- После нового фото или выбора изображения запускается локальная bundled ML Kit Text Recognition. `ReceiptOcrParser` предлагает позиции с суммами и рамками; до переноса неподтверждённых предложений выводится предупреждение. Можно изменить позиции, назначить участников, разметить вручную или повторить распознавание. Модель для латиницы плохо подходит для русских чеков: **настоящие русские чеки и OCR на физическом устройстве пока не проверены**, результат нельзя считать гарантированным.
- `BillDraftStore` отдельно от сохранённых счетов держит черновики по деморежиму/UID аккаунта; форма сохраняется при уходе в фон и возврате назад. При возврате из редактора чека фото и разметка остаются в черновике, при сохранении фото переносится в основное хранилище, черновик удаляется. Есть продолжение и удаление с главного экрана.
- Компиляция требует Android SDK Platform 33, `minSdkVersion` остаётся 28. `Money.parse` проверяет границы без вызова `Math.multiplyExact` (Android lint на minSdk 28 считал его API 31). Сборка и 48 локальных тестов проходят; `lintDebug` заканчивается успешно, но AGP 4.1.3 выдаёт `NoClassDefFoundError: ...Vendor` для lint.jar новых AndroidX — часть проверок зависимостей не запускается. Не считать lint полностью покрывающим новые зависимости.
- На эмуляторе Android 11 установлен демопакет: вручную создан черновик с названием, выполнен возврат назад, проверены его появление на главном экране, восстановление и удаление. Сценарий реального OCR с фото, создание/поворот/восстановление нескольких снимков и проверка облачного аккаунта на устройстве всё ещё нужны.

Бесплатный тариф имеет квоты и использует переданные данные для улучшения продуктов; при включённом биллинге возможна оплата. Не встраивать ключ в APK/репозиторий и не отправлять фото в фоне.
- В исходниках добавлены `GeminiReceiptClient` (уменьшенное JPEG по HTTPS, структурированные позиции без выдуманных координат, проверка сумм) и `ReceiptAiKey` (Android Keystore AES-GCM, без бэкапа ключа), подтверждения в `ReceiptActivity`; офлайн-режим остаётся, результат только предварительный и редактируемый. При ошибке сети старые позиции сохраняются. Пока **нет пользовательского API-ключа, реальный сетевой вызов и качество на настоящих чеках не проверены**. Нужно собрать и предложить проверочный APK `1.4.2-rc4`, не объявляя стабильный релиз.
- На эмуляторе Android 11 вручную открыты фото чека и диалог ввода ключа, проверено, что фото не отправляется без отдельного действия. Инструментальный тест проверил сохранение/чтение/удаление ключа в Android Keystore. 54 модульных теста и 3 инструментальных теста прошли, `lintDebug` завершается успешно (AGP 4.1.3 имеет уже известное ограничение по новым AndroidX lint-проверкам). Модульный тест HTTP-обвязки использует поддельное соединение, **не настоящий API**.
